# Online Modelling for Real-Time Chiller Efficiency Optimization — code and paper (NLPIR 2026 submission)

Companion repository for the paper *Online Modelling for Real-Time Chiller Efficiency Optimization: A Verified
Co-Simulation Testbed with Load Forecasting, Online Efficiency Tracking and Staging-Decision Analysis*
(M. Esmail, T. Y. Chai; Universiti Tunku Abdul Rahman). Everything in the paper — every table value and figure —
is generated by the code in this repository. **All results are from simulation (synthetic weather, synthetic
chiller curves, placeholder tariff); no measured plant data was used.**

## Repository layout

```
README.md            this file
requirements.txt     Python dependencies
run_all.sh           runs every experiment, then check_results.py
*.py                 simulator, experiments and checks (see "Code structure" below)
figs/                figures produced by the run (Figures 1-8)
results_*.json       numeric results produced by the run
expected_output/     results and figures from the reference run, for comparison
paper/               LaTeX source (Springer svproc class), figures and compiled paper.pdf
```

## Reproduce the paper's numbers in three steps

1. `pip install -r requirements.txt` (Python 3.10+; reference run: Python 3.13, NumPy 2.5, SciPy 1.18,
   Matplotlib 3.11, scikit-learn 1.9)
2. `bash run_all.sh` (about one minute)
3. Read the last lines of the output. `check_results.py` compares 35 values reported in the paper with the fresh run
   and prints `All reported values reproduced.` if they agree within tolerance. Differences of a few tenths of a
   per cent in the forecasting values can occur with other scikit-learn versions; this is covered by the tolerances.

To rebuild the paper: `cd paper && pdflatex paper && pdflatex paper` (needs a standard TeX Live; the class file
`svproc.cls` is included).

## Detailed documentation of the code (testbed, Phase 1 and Phase 2)

Code that generates every number and figure in the Phase 1 report *Online Modelling for Real-Time Chiller Efficiency
Optimization* and in the Phase 2 results built on the same testbed.

- **Phase 1:** a verified simulation environment and a conventional-control reference case (scheduled PI control, and
  rule-based pre-cooling as an intermediate benchmark). No AI component.
- **Phase 2:** short-horizon cooling-load forecasting (walk-forward evaluation), online identification of chiller
  efficiency by recursive least squares under injected drift, and a quasi-static analysis of how forecast and model
  errors affect the choice of how many chillers to run. **No predictive controller (MPC) yet.**

## Quick start

Requires Python 3.10 or later. It was developed with Python 3.13, NumPy 2.5, SciPy 1.18, Matplotlib 3.11 and scikit-learn 1.9.

```bash
pip install -r requirements.txt
bash run_all.sh
```

Without bash (for example on Windows), run the commands inside `run_all.sh` one by one:

```bash
python make_architecture.py
python run_phase1.py
python run_validation.py
python run_phase2.py
python check_results.py
```

The whole run takes about a minute on a laptop (Phase 1 about 10 seconds, Phase 2 about 55 seconds). The weather
generator uses a fixed seed (`seed=7`) and every random draw in Phase 2 is seeded, so repeated runs give identical output.
Phase 1 values are independent of the scikit-learn version; the Phase 2 forecasting values can differ slightly between
scikit-learn versions, and `check_results.py` allows a small tolerance for them.

The folder `expected_output/` holds the results and figures from the reference run, for comparison.

## Code structure

| Module | Responsibility |
|---|---|
| `weather.py` | Synthetic tropical weather (seeded) and occupancy schedule |
| `building.py` | 3R2C thermal model, RK4 and exact (matrix-exponential) integration, state-space export for the Phase 3 MPC |
| `chiller.py` | DOE-2 / EnergyPlus Electric EIR chiller curves, cooling tower, pumps, staging logic, COP mapping, AHRI rating |
| `tariff.py` | Time-of-use energy charge and maximum-demand charge |
| `controllers.py` | Scheduled PI thermostat (baseline) and rule-based pre-cooling |

| `validation.py` | Verification, benchmarks, sensitivity, ASHRAE Guideline 14 statistics |
| `forecast.py` | Phase 2: load-forecasting features, walk-forward evaluation, metrics |
| `online_cop.py` | Phase 2: recursive least squares estimators and the two injected drift scenarios |
| `staging.py`, `analysis.py` | Phase 2: power as a function of the number of running chillers; decision-loss analysis |

| `check_results.py` | Compares a fresh run with the report |

## Changing the settings

- **Time step:** `simulate(dt_h=0.25)` is the default (15 minutes).
- **Run length and weather:** `simulate(days=14, seed=7)`.
- **Building and plant parameters:** `simulate(bp={...}, pp={...})`, for example `bp={'Gao': 10.0}` or `pp={'cop_scale': 0.95}`.
- **Tariff:** constants at the top of `tariff.py`.
- **Control strategies:** `controllers.py`; select with `simulate('baseline')` or `simulate('precool')`.

## Limitations

These matter when interpreting any output:

- **Not calibrated.** No measured plant or building data was used. Absolute energy values (±25 % under
  parameter perturbation) must not be read as predictions for a real building. The relative energy comparison
  between strategies is more robust (3.9–5.9 % across the sensitivity cases); the cost gap is much less so.
- **The cost gap depends on a controller limit, not only on the plant.** The PI output limit `umax`
  (`controllers.PI`) is a tuning constant. At the 340 kW value used in the first version of this work, the
  pre-cooling strategy saturated the controller at four steps and its demand peak — which drives the entire cost
  penalty — fell on one of them, while the baseline never saturated. `umax` is now 400 kW, high enough that it
  never binds in either strategy. Sweeping it moves the cost gap from +2.1 % (300) through +7.3 % (340) to
  +9.0 % (400 and above), while the energy gap stays at 4.13–4.27 %. Treat every cost figure here as indicative,
  and sweep controller parameters, not only building parameters, before quoting one.
- **Synthetic chiller curves.** Coefficients are not from a manufacturer catalogue. The AHRI figures are a
  plausibility check, not a validation.
- **Synthetic weather.** The weather file is generated, not measured.
- **Placeholder tariff.** Rates are of the right order of magnitude but must be replaced with the published
  schedule before any cost figure is quoted.
- **Indicative benchmark ranges.** The ranges in `validation.benchmarks()` should be replaced with cited values.
- **Phase 2 is evaluated on simulated data.** The load is a smooth response of the same simulator that generated the
  weather, so forecast errors are lower than they would be for a real building, and the weather-forecast errors are
  assumed values (`forecast.FCST_ERR`). The drift scenarios are injected by hand; they test whether the estimators track
  a known change, not whether real plants drift in this way.
- **Staging analysis is quasi-static.** It ignores start-up transients, minimum run times and the thermal storage in the
  building mass, so the staging headroom it reports is not an estimate of what a controller would save in operation.
  The headroom also costs 41 % more stage changes than the rule makes (532 against 377 over 120 days), which the
  analysis does not charge for; `headroom()` reports both counts.
- **Little to optimise on this plant.** The quasi-static optimum picks the minimum feasible number of chillers on
  98 % of scheduled steps, so optimal staging here is almost the trivial policy "run as few machines as the load
  allows". Conclusions about the value of a learning layer should not be generalised from one plant configuration.
- **No recurrent-network baseline** is included yet; the forecasting comparison is persistence, seasonal naive, ridge
  regression and gradient boosting.
